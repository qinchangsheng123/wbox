C 案为什么会糊，怎么修的

3× 放大 · 16px 图标框

上一版 C 案是 4px 点贴在图标框右上角的里面。三条原因叠在一起，必糊： 一是直径只有 4px，1px 底环一扣就剩 2px 实心，肉眼只剩一团灰； 二是位置在框内，16px 图标的安全边距只有 2px，点一定压在图标线条上，线条和点互相啃； 三是 Tk 的 create_oval 没有抗锯齿，4px 圆在半像素坐标上会被画成阶梯块。 修法对应三条：加到 7px、圆心搬到图标框外沿、用项目已有的 sprite.coverage 做 4×4 超采样。
第四条是文字修不了的：关闭态不挂角标。图标本身就是灰的（t2 × 0.84）， 再挂一枚 t4 灰点，两者只差一档亮度，任何直径都分不开——这是 C 案只能放弃关闭态标记的原因。

状态口径（三档共用）

一套判定

数据来自加载期 entry.status、守护写的 plugins_state.json （status / error_count / ticks）、开关值、requires_admin。 判定顺序沿用 plugin_hint()：加载期状态优先，运行期 degraded / error_count > 0 覆盖。

守护 / 加载状态点的色版本号行里还会发生什么
ok + 开关开 ont3常态
ok + 开关关 t4t4整行降噪。A 案画灰点；C 案不挂——灰点贴灰图标分不开
degraded / error_count > 0 dangerfg展开行补错误摘要
load_failed · bad_manifest
too_new · conflict		——这类插件本来就不进列表（entries 只收 STATUS_OK）， 它们在「设置 → 插件」组里有整行说明
requires_admin 且未提权 ont3点仍是绿（它没坏），展开行顶部写「需要管理员」

红点的例外仍然成立：极简的铁律是 danger 只给破坏性操作， 这里破例给「运行异常」，因为它是数据状态而非装饰，且同时把版本号提到 fg——不只靠颜色区分。 A / C 两档都一样：不想出现红，就换 fg 实心点，改一处取色。
